# 実装指針：フロントエンド

## 1. 概要

本ドキュメントでは、練習表自動生成システムのフロントエンド実装に関する指針について説明します。このガイドラインは、UI/UXの品質確保、保守性の向上、および開発の効率化を目的としています。

## 2. 技術スタック

### 2.1 コア技術

- **フレームワーク**: Next.js 14.x
- **言語**: TypeScript 5.x
- **状態管理**: React Context API + Zustand
- **ルーティング**: Next.js App Router
- **UIコンポーネント**: Material-UI (MUI) 5.x
- **フォーム管理**: React Hook Form + Zod
- **バックエンド連携**: Supabase JavaScript Client

### 2.2 開発ツール

- **ビルドツール**: Next.js ビルドシステム
- **テストフレームワーク**: Jest + React Testing Library
- **リンター/フォーマッター**: ESLint + Prettier
- **API連携**: Supabase SDK + React Query

## 4. コンポーネント設計

### 4.1 コンポーネント分類

- **プレゼンテーショナルコンポーネント**: UI表示に特化し、状態を持たない
- **コンテナコンポーネント**: ビジネスロジックと状態管理を担当
- **ページコンポーネント**: ルーティングに対応するトップレベルコンポーネント
- **レイアウトコンポーネント**: 共通のページレイアウトを提供

### 4.2 命名規則

- コンポーネントファイル: パスカルケース（例: `ScheduleList.tsx`）
- フックファイル: キャメルケース、`use`プレフィックス（例: `useScheduleData.ts`）
- ユーティリティファイル: キャメルケース（例: `dateFormatter.ts`）

### 4.3 コンポーネント実装の概要

スケジュールカードコンポーネントは以下の要素で構成されます：

- TypeScriptの型定義を使用した強力な型付けインターフェース
- コンポーネントのドキュメント化（JSDoc形式のコメント）
- 練習日時、場所、ステータスなどの情報表示領域
- 詳細表示と編集のためのアクションボタン

このコンポーネントは純粋な関数型コンポーネントとして実装され、外部から渡されたデータを表示するだけの責務を持ちます。状態管理やロジックは含まず、親コンポーネントから受け取るコールバック関数を使用してイベントを伝播します。

## 5. 状態管理

### 5.1 状態の分類

- **ローカル状態**: 単一コンポーネント内のみで使用される状態（React useState）
- **グローバル状態**: アプリケーション全体で共有される状態（Zustand）
- **サーバー状態**: Supabaseから取得するデータ（React Query + Supabase）

### 5.2 Zustand状態管理の概要

Zustandを使用したスケジュール管理ストアは以下の要素で構成されます：

- スケジュール一覧、選択中のスケジュール、ローディング状態、エラー情報などの状態
- スケジュール一覧を取得する非同期アクション（Supabase連携）
- スケジュールを選択・解除するアクション

ストアは複数のコンポーネントからアクセス可能で、状態更新時は関連するコンポーネントのみが再レンダリングされます。エラーハンドリングを内蔵しており、API通信の失敗時には適切なエラーメッセージが保存されます。

## 6. フォーム実装

### 6.1 基本方針

- React Hook Formを使用してフォーム状態を管理
- Zodを使用してバリデーションスキーマを定義
- フィールド単位のバリデーションと表示

### 6.2 フォーム実装の概要

スケジュールフォームは以下の要素で構成されます：

- Zodによる厳格なバリデーションスキーマ（必須項目、時間の前後関係チェックなど）
- React Hook Formとzodを連携させたフォーム状態管理
- Material-UIのGrid、TextFieldを活用したレスポンシブレイアウト
- フィールドごとのエラー表示とヘルパーテキスト
- 初期値の設定と送信処理のカスタマイズ
- 送信中の状態表示（ボタンの無効化など）

フォームはサブミット時に親コンポーネントに値を渡し、バリデーションはすべてクライアント側で完結します。日付や時間の入力にはHTML5の標準入力タイプを活用し、ユーザビリティを向上させています。

## 7. APIとの連携

### 7.1 基本方針

- Supabase SDKを使用してAPI呼び出しを行う
- React Queryを使用してサーバー状態を管理
- インターセプターを使用して共通のエラー処理を実装

### 7.2 Supabase SDKの活用概要

Supabase SDKを使用したクライアント実装は以下の要素で構成されます：

- 環境変数を使用した安全な接続情報の管理
- 型安全なデータベースクライアントの初期化
- 認証関連機能（サインイン、サインアウト、ユーザー情報取得）をまとめたカスタムフック

クライアントは一度だけ初期化され、アプリケーション全体で再利用されます。環境変数が設定されていない場合は、明示的なエラーを投げることで早期に問題を発見できるようにしています。

### 7.3 React Queryの活用概要

React Queryを使用したデータフェッチングは以下の要素で構成されます：

- チームIDに基づくスケジュール一覧取得フック（キャッシュと失効制御付き）
- スケジュールIDに基づく詳細情報取得フック（条件付き実行機能付き）
- スケジュール作成・更新ミューテーションフック（キャッシュ更新機能付き）

これらのフックはコンポーネントから簡単に利用でき、ローディング状態やエラー状態も含めた豊富なリターン値を提供します。不要な再取得を防ぐためのキャッシュ戦略が組み込まれており、パフォーマンスとユーザー体験を向上させています。

## 8. パフォーマンス最適化

### 8.1 主要最適化手法

- **コンポーネントのメモ化**: `React.memo`、`useMemo`、`useCallback`の適切な使用
- **コード分割**: `React.lazy`と`Suspense`を使用した動的インポート
- **仮想スクロール**: 大量リストの表示に`react-window`や`react-virtualized`を使用
- **画像最適化**: WebPフォーマットの使用、適切なサイズ指定
- **バンドルサイズ最適化**: ツリーシェイキングの活用、不要なライブラリの削除

### 8.2 最適化実装の概要

#### コード分割と遅延ロード
大きなコンポーネント（カレンダービューなど）は遅延ロードを活用します。これにより初期バンドルサイズが削減され、初回ロード時間が短縮されます。コンポーネントがロードされるまでの間はローディングインジケータを表示し、ユーザー体験を向上させます。

#### 仮想スクロール実装
大量のスケジュールリストを表示する際は、react-windowライブラリを活用した仮想スクロールを実装します。実際に画面に表示されている要素のみをレンダリングすることで、メモリ使用量とレンダリング時間を大幅に削減します。リスト項目の高さを固定し、オーバースキャン（画面外の要素の先読み）を適切に設定することでスムーズなスクロール体験を実現します。

### 8.3 Supabase連携の概要

Supabaseクライアントの実装では、以下の点に注意します：

- 環境変数の確実な検証とエラーハンドリング
- 型安全なクライアント構築によるコンパイル時のエラー検出
- 認証関連機能をカスタムフックにまとめ、再利用性を高める

これにより、安全で保守性の高いバックエンド連携が可能になります。

### 8.4 リアルタイムデータ更新の概要

Supabaseのリアルタイム機能を活用したデータ更新の実装には以下の要素が含まれます：

- チームIDに基づく初期データの取得
- Supabaseチャネルを使用したリアルタイムサブスクリプション
- イベントタイプ（挿入、更新、削除）に応じた状態更新ロジック
- コンポーネントのアンマウント時のクリーンアップ処理

これにより、複数ユーザーが同時に作業する環境でもデータの一貫性が保たれ、常に最新の情報が表示されます。状態更新は関数型アップデートを使用して行われ、競合状態を防止します。

## 10. テスト戦略

### 10.1 テスト階層

- **単体テスト**: コンポーネントとフックの個別テスト
- **統合テスト**: コンポーネント間の連携テスト
- **E2Eテスト**: Cypress を使用したエンドツーエンドテスト

### 10.2 テスト実装の概要

スケジュールカードコンポーネントのテストでは以下の点を検証します：

- レンダリング結果の正確性（日付、時間、場所、ステータスなどの情報が正しく表示されるか）
- ユーザーインタラクションの動作確認（詳細ボタンや編集ボタンのクリックイベント）
- コールバック関数の呼び出し検証（正しい引数でコールバックが呼ばれるか）

テストには、モックデータとモック関数を活用し、コンポーネントを独立した環境でテストします。各テスト実行前に状態をリセットすることで、テスト間の影響を排除します。

単体テストでは特定のコンポーネントまたはフックの動作のみを検証し、統合テストではコンポーネント間の連携を確認します。E2Eテストでは実際のユーザーフローを模倣して、アプリケーション全体の動作を検証します。

## 11. まとめ

フロントエンド実装では、以下の点を重視して開発を進めます：

- 一貫したコンポーネント設計とコーディング規約の遵守
- 型安全性を確保するTypeScriptの積極的な活用
- 適切な状態管理とAPI連携パターンの採用
- パフォーマンスとアクセシビリティへの配慮
- テスト駆動開発の実践

これらの指針に従うことで、高品質で保守性の高いフロントエンドを実現します。
