# 実装指針：基本方針

## 1. 概要

本ドキュメントでは、練習表自動生成システムの実装に関する基本指針について説明します。開発チーム全体で一貫した実装アプローチを採用することで、コードの品質、保守性、そして拡張性を確保します。

本指針は、開発プロセス全体を通じて参照されるべきガイドラインであり、コードレビューの基準としても活用されます。ただし、プロジェクトの進行や技術の進化に応じて、適宜見直しと更新を行うことを前提としています。

## 2. コーディングスタイル

### 2.1 一般原則

- **読みやすさを優先**: 短いコードよりも読みやすいコードを優先する
- **シンプルさ**: 複雑な実装よりもシンプルな実装を優先する
- **DRY原則**: 同じコードを繰り返し書かない（Don't Repeat Yourself）
- **KISS原則**: シンプルに保つ（Keep It Simple, Stupid）
- **YAGNI原則**: 必要になるまで機能を追加しない（You Aren't Gonna Need It）

### 2.2 コード構造

- **関数/メソッドの長さ**: 1つの関数/メソッドは原則として30行以内に収める
- **ファイルの長さ**: 1つのファイルは500行を超えないようにする
- **パラメータの数**: 関数/メソッドのパラメータは4つ以下に抑える
- **入れ子の深さ**: 制御構造の入れ子は3レベル以内に抑える

### 2.3 コメント

- **コードドキュメンテーション**: すべての公開API、クラス、関数にはドキュメントコメントを付ける
- **複雑なロジック**: 複雑なロジックや非直感的なコードには説明コメントを付ける
- **TODOコメント**: 将来の変更や課題には`TODO:`または`FIXME:`プレフィックス付きのコメントを使用する
- **不要なコメント**: コード自体が説明的である場合は冗長なコメントを避ける

## 3. 命名規則

### 3.1 一般原則

- **命名の目的**: 名前は目的や意図を明確に表現すべき
- **省略の回避**: 意味不明な省略や短縮は避ける（例: `calculateTotal`を`calcTot`としない）
- **一貫性**: プロジェクト全体で一貫した命名規則を使用する

### 3.2 具体的な命名規則

| 項目 | 規則 | 例 |
|------|------|-----|
| ファイル名 | キャメルケース（コンポーネントの場合はパスカルケース） | `scheduleService.ts`, `UserProfile.tsx` |
| クラス名 | パスカルケース | `ScheduleGenerator`, `TeamRepository` |
| インターフェース名 | パスカルケース、接頭辞「I」なし | `Repository`, `UserService` |
| 型名 | パスカルケース | `ScheduleStatus`, `PlayerPosition` |
| 変数名 | キャメルケース | `currentUser`, `teamList` |
| 定数名 | 大文字のスネークケース | `MAX_TEAM_SIZE`, `DEFAULT_DURATION` |
| 関数名 | キャメルケース、動詞で開始 | `calculateTotal`, `getUserById` |
| プライベートメンバー | キャメルケース、アンダースコアで開始 | `_privateMethod`, `_internalState` |
| 列挙型 | パスカルケース | `enum UserRole { Admin, Coach, Player }` |

### 3.3 特殊な命名パターン

- **真偽値変数**: `is`, `has`, `can`などの接頭辞を使用（例: `isActive`, `hasPermission`）
- **イベントハンドラ**: `handle`や`on`で開始（例: `handleSubmit`, `onUserLogin`）
- **非同期関数**: 必要に応じて`async`接頭辞を使用（例: `asyncFetchData`）
- **コールバック関数**: `callback`や`cb`で終わる（例: `saveCallback`, `loadCb`）

## 4. エラー処理

### 4.1 一般原則

- **明示的なエラーハンドリング**: すべての潜在的なエラーを明示的に処理する
- **意味のあるエラーメッセージ**: エラーメッセージは具体的で、問題の原因と可能な解決策を示す
- **エラーの種類の区別**: 異なる種類のエラー（ビジネスルール違反、技術的エラー、外部サービスエラーなど）を明確に区別する

### 4.2 例外の使用

- **例外の範囲**: 例外は予期しない状況や回復不可能なエラーのために使用
- **例外の粒度**: 細かい粒度で具体的な例外クラスを定義する
- **例外のラッピング**: 低レベルの例外はより意味のある高レベルの例外にラップする

### 4.3 エラー処理パターン

#### TypeScriptでのエラー処理例

```typescript
try {
  const schedule = await scheduleService.createSchedule(scheduleData);
  return res.status(201).json(schedule);
} catch (error) {
  if (error instanceof ValidationError) {
    // ビジネスルール違反の場合
    return res.status(400).json({
      error: 'バリデーションエラー',
      details: error.details,
      code: 'VALIDATION_ERROR'
    });
  } else if (error instanceof AuthorizationError) {
    // 権限エラーの場合
    return res.status(403).json({
      error: '権限エラー',
      message: error.message,
      code: 'AUTHORIZATION_ERROR'
    });
  } else {
    // 予期しないエラーの場合
    logger.error('予期しないエラーが発生しました', { error });
    return res.status(500).json({
      error: 'サーバーエラー',
      message: '操作を完了できませんでした。しばらく経ってからもう一度お試しください。',
      code: 'INTERNAL_ERROR'
    });
  }
}
```

#### 非同期エラー処理パターン

```typescript
// Promise.catchを使用したパターン
fetchData()
  .then(data => processData(data))
  .catch(error => handleError(error));

// async/awaitを使用したパターン
async function fetchAndProcessData() {
  try {
    const data = await fetchData();
    return processData(data);
  } catch (error) {
    handleError(error);
    throw new ApplicationError('データ処理に失敗しました', { cause: error });
  }
}
```

### 4.4 ログレベルとエラー通知

| 状況 | ログレベル | 通知 |
|------|------------|------|
| デバッグ情報 | DEBUG | なし |
| 通常の処理情報 | INFO | なし |
| 警告（潜在的な問題） | WARN | 監視システムに記録 |
| エラー（回復可能） | ERROR | 監視システムに通知 |
| 致命的なエラー | FATAL | 即時通知（メール/Slack） |

## 5. 型安全性

### 5.1 静的型付け

- **明示的な型指定**: 変数、関数のパラメータ、戻り値には明示的に型を指定する
- **any型の回避**: TypeScriptの`any`型の使用は極力避ける
- **ジェネリクス**: 適切な場所でジェネリクスを活用する
- **型ガード**: 型の安全性を確保するために型ガードを使用する

### 5.2 型定義の例

```typescript
// 明示的な型定義
interface ScheduleParams {
  teamId: string;
  practiceDate: Date;
  duration: number;
  location: string;
  notes?: string;
}

// ジェネリクスの使用
class Repository<T, ID> {
  findById(id: ID): Promise<T | null>;
  findAll(): Promise<T[]>;
  save(entity: T): Promise<T>;
  update(id: ID, entity: Partial<T>): Promise<T>;
  delete(id: ID): Promise<boolean>;
}

// 型ガードの例
function isSchedule(obj: any): obj is Schedule {
  return obj && typeof obj === 'object' 
    && typeof obj.id === 'string'
    && obj.practiceDate instanceof Date;
}
```

## 6. テスト

### 6.1 テスト原則

- **自動化**: すべてのテストは自動化され、CI/CDパイプラインの一部として実行可能
- **独立性**: 各テストは他のテストに依存せず、どのような順序でも実行可能
- **再現性**: テストは決定論的で、同じ入力に対して常に同じ結果を返す
- **網羅性**: コードカバレッジだけでなく、機能的な網羅性も重視する

### 6.2 テストの種類と方針

| テストタイプ | 対象 | カバレッジ目標 | テストツール |
|------------|------|--------------|------------|
| ユニットテスト | 関数、クラス、コンポーネント | ロジック行の80%以上 | Jest, React Testing Library |
| 統合テスト | 複数のモジュールの連携 | 主要フロー100% | Jest, Supertest |
| E2Eテスト | エンドツーエンドの機能 | クリティカルパス100% | Cypress |
| パフォーマンステスト | 応答時間、スループット | 主要API | k6, Lighthouse |

### 6.3 テストコードの例

```typescript
// ユニットテストの例
describe('ScheduleService', () => {
  let service: ScheduleService;
  let mockRepository: jest.Mocked<ScheduleRepository>;
  
  beforeEach(() => {
    mockRepository = {
      findById: jest.fn(),
      save: jest.fn(),
      // ...他のメソッド
    } as any;
    
    service = new ScheduleService(mockRepository);
  });
  
  describe('createSchedule', () => {
    it('有効なデータで新しい練習表を作成できること', async () => {
      // 準備
      const scheduleData = {
        teamId: 'team-123',
        practiceDate: new Date(),
        duration: 120
      };
      
      mockRepository.save.mockResolvedValue({
        id: 'schedule-456',
        ...scheduleData,
        status: 'DRAFT',
        createdAt: new Date()
      });
      
      // 実行
      const result = await service.createSchedule(scheduleData);
      
      // 検証
      expect(result).toHaveProperty('id', 'schedule-456');
      expect(result.status).toBe('DRAFT');
      expect(mockRepository.save).toHaveBeenCalledWith(
        expect.objectContaining(scheduleData)
      );
    });
    
    it('無効なデータの場合はエラーをスローすること', async () => {
      // 準備
      const invalidData = {
        teamId: 'team-123',
        // practiceDate が欠けている
        duration: -10 // 無効な値
      };
      
      // 実行と検証
      await expect(service.createSchedule(invalidData as any))
        .rejects.toThrow(ValidationError);
    });
  });
});
```

## 7. パフォーマンスと最適化

### 7.1 一般原則

- **早期最適化の回避**: 「早すぎる最適化は諸悪の根源」の原則に従い、測定可能な問題に対してのみ最適化を行う
- **ボトルネックの特定**: プロファイリングツールを使用して実際のボトルネックを特定する
- **測定駆動**: 最適化の前後で測定を行い、効果を検証する

### 7.2 フロントエンド最適化

- **バンドルサイズ**: コード分割とレイジーローディングを活用
- **レンダリングパフォーマンス**: 不要な再レンダリングを防止（React.memo, useMemo, useCallback）
- **アセット最適化**: 画像の最適化、適切なフォーマット（WebP）の使用
- **キャッシュ戦略**: 適切なキャッシュヘッダーの設定

### 7.3 バックエンド最適化

- **データベースクエリ**: インデックスの適切な設定、N+1問題の回避
- **キャッシング**: 適切なレベルでのキャッシュ実装（メモリ、Redis）
- **接続プーリング**: データベース接続の効率的な再利用
- **非同期処理**: 長時間実行タスクのバックグラウンド処理

### 7.4 最適化の例

```typescript
// Reactのパフォーマンス最適化例
// メモ化を使用して不要な再計算を防止
const MemoizedComponent = React.memo(({ data }) => {
  // 高コストな計算をメモ化
  const processedData = useMemo(() => {
    return expensiveCalculation(data);
  }, [data]);
  
  return <div>{processedData}</div>;
});

// データベースクエリの最適化例
async function getTeamWithPlayers(teamId: string): Promise<TeamWithPlayers> {
  // N+1問題を回避するためのJOINクエリ
  const team = await prisma.team.findUnique({
    where: { id: teamId },
    include: { players: true }
  });
  
  if (!team) {
    throw new NotFoundError(`ID ${teamId} のチームが見つかりません`);
  }
  
  return team;
}
```

## 8. セキュリティ

### 8.1 一般原則

- **デフォルトで安全**: セキュリティはすべての機能の基本要件として考慮
- **多層防御**: 単一の防御層に頼らず、複数のセキュリティ層を設ける
- **最小権限の原則**: 必要最小限の権限のみを付与

### 8.2 一般的な脆弱性対策

| 脆弱性 | 対策 |
|-------|------|
| インジェクション攻撃 | パラメータ化クエリ、ORM、入力検証 |
| クロスサイトスクリプティング(XSS) | 出力エスケープ、CSP、ReactのJSX |
| CSRF | Anti-CSRFトークン、SameSiteクッキー |
| 認証の脆弱性 | 強力なパスワードポリシー、多要素認証 |
| 認可の脆弱性 | 一貫した認可チェック、RBAC |
| センシティブデータの漏洩 | 暗号化、アクセス制御、データの最小化 |

### 8.3 セキュアコーディング例

```typescript
// パラメータ化クエリの使用
async function getUserByEmail(email: string): Promise<User | null> {
  return await prisma.user.findUnique({
    where: { email: email.toLowerCase() }
  });
}

// ユーザー入力の検証
function validateUserInput(input: unknown): UserInput {
  const schema = z.object({
    username: z.string().min(3).max(50),
    email: z.string().email(),
    password: z.string().min(8).regex(/[A-Z]/).regex(/[0-9]/)
  });
  
  return schema.parse(input);
}

// 適切な認可チェック
async function updateSchedule(
  userId: string, 
  scheduleId: string, 
  data: ScheduleUpdateInput
): Promise<Schedule> {
  const schedule = await scheduleRepository.findById(scheduleId);
  
  if (!schedule) {
    throw new NotFoundError('練習表が見つかりません');
  }
  
  const team = await teamRepository.findById(schedule.teamId);
  
  // ユーザーが権限を持っているか確認
  if (team.coachId !== userId && !await isAdminUser(userId)) {
    throw new ForbiddenError('この操作を実行する権限がありません');
  }
  
  return await scheduleRepository.update(scheduleId, data);
}
```

## 9. コード品質管理

### 9.1 静的解析ツール

以下のツールを活用して、コードの品質と一貫性を確保します：

- **ESLint**: コードスタイルとパターンの検証
- **Prettier**: コードフォーマットの自動化
- **TypeScript コンパイラ**: 型チェック
- **SonarQube**: コード品質とセキュリティの包括的分析

### 9.2 コードレビュープロセス

- すべてのコード変更は少なくとも1人の他の開発者によるレビューを受ける
- コードレビューは具体的なフィードバックを提供し、コードの改善に焦点を当てる
- レビューチェックリストを用意し、一貫した品質基準を適用する

### 9.3 継続的インテグレーション

- すべてのプルリクエストに対して以下を実行：
  - ビルド検証
  - 静的解析
  - 自動テスト実行
  - コードカバレッジレポート
- 品質基準を満たさないコードは本番環境にマージできない仕組みを構築

## 10. ドキュメンテーション

### 10.1 コード内ドキュメント

- すべての公開API、クラス、関数には適切なドキュメントコメントを付ける
- コメントはなぜそのコードが存在するのか、どのように動作するのかを説明する
- 複雑なアルゴリズムやビジネスロジックには追加の説明を提供する

### 10.2 技術ドキュメント

- アーキテクチャの概要と主要コンポーネント
- 開発環境のセットアップ手順
- ビルドとデプロイのプロセス
- 主要なワークフローとユースケース
- トラブルシューティングガイド

### 10.3 APIドキュメント

- RESTful APIの場合はOpenAPI（Swagger）を使用
- エンドポイント、パラメータ、レスポンス形式を明確に文書化
- 認証要件とエラーレスポースを記述
- 実際の使用例を提供

## 11. バージョン管理とブランチ戦略

### 11.1 バージョン管理

- [セマンティックバージョニング](https://semver.org/)を採用
  - メジャーバージョン（X.y.z）: 後方互換性のない変更
  - マイナーバージョン（x.Y.z）: 後方互換性のある機能追加
  - パッチバージョン（x.y.Z）: バグ修正

### 11.2 ブランチ戦略

- GitFlowまたはGitHub Flowを採用
- 主要ブランチ:
  - `main`/`master`: 本番リリース用
  - `develop`: 開発統合用
  - `feature/*`: 新機能開発用
  - `bugfix/*`: バグ修正用
  - `release/*`: リリース準備用
  - `hotfix/*`: 緊急修正用

### 11.3 コミットメッセージ

- [Conventional Commits](https://www.conventionalcommits.org/)形式を採用
- 例:
  - `feat: 練習表自動生成機能の追加`
  - `fix: 練習表保存時のバリデーションエラーを修正`
  - `docs: APIドキュメントの更新`
  - `refactor: スケジュールサービスのリファクタリング`

## 12. 依存関係管理

### 12.1 パッケージ管理

- 依存パッケージはpackage.jsonで明示的に管理
- バージョンは可能な限り固定（`^`や`~`の使用を最小限に）
- 定期的にパッケージを更新し、セキュリティ脆弱性をチェック

### 12.2 依存関係の選定基準

- 活発なメンテナンス状況
- コミュニティのサポート状況
- ライセンスの互換性
- バンドルサイズへの影響
- セキュリティ履歴

### 12.3 モノレポ管理

- 大規模プロジェクトではYarnワークスペースまたはNX等を検討
- パッケージ間の依存関係を明確に管理
- 共通コードのライブラリ化を促進

## 13. 環境分離とデプロイ

### 13.1 環境分離

- **開発環境**: 開発者ローカル環境
- **テスト環境**: CI/CD統合テスト用
- **ステージング環境**: 本番同等の検証環境
- **本番環境**: エンドユーザー向け環境

### 13.2 環境設定

- 環境変数を使用して環境ごとの設定を管理
- 機密情報はシークレット管理サービスを使用
- 各環境の違いを明確にドキュメント化

### 13.3 デプロイ戦略

- CI/CDパイプラインを使用した自動デプロイ
- ブルー/グリーンデプロイまたはカナリアリリースの検討
- ロールバック手順の整備

## 14. まとめ

本ドキュメントで示した実装指針は、練習表自動生成システムの開発における基本方針を示しています。これらの指針は、開発チーム全体でコードの品質と一貫性を確保するために活用されるべきものです。

各開発者は本指針を理解し、日々の開発作業に適用することが期待されます。同時に、指針自体も開発プロセスの進行とともに進化させていくことが重要です。

疑問点や改善提案がある場合は、開発チームでの議論を通じて本ドキュメントの更新を検討してください。
