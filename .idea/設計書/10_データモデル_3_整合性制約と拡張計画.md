## 5. データモデルの整合性制約

データモデル全体の整合性を確保するための重要な制約について説明します。

### 5.1 エンティティ間の整合性制約

#### 5.1.1 スケジュールとセッションの整合性

スケジュールとセッションの間の整合性を確保するための制約です。

1. **日付範囲の制約**
   - セッションの日付はスケジュールの開始日～終了日の範囲内でなければならない
   - アプリケーションレベルでの検証を実施

```sql
-- セッション作成時のトリガー
DELIMITER //
CREATE TRIGGER validate_session_date BEFORE INSERT ON practice_sessions
FOR EACH ROW
BEGIN
    DECLARE schedule_start DATE;
    DECLARE schedule_end DATE;
    
    SELECT start_date, end_date INTO schedule_start, schedule_end
    FROM schedules WHERE schedule_id = NEW.schedule_id;
    
    IF NEW.date < schedule_start OR NEW.date > schedule_end THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Session date must be within schedule date range';
    END IF;
END //
DELIMITER ;
```

2. **スケジュールステータスによる操作制限**
   - 公開済みスケジュールに対するセッションの追加・修正・削除は制限される
   - 特定の権限を持つユーザーのみ可能

#### 5.1.2 メンバーと割当の整合性

1. **監督者資格の制約**
   - 監督者として割り当てられるメンバーは監督者資格（can_supervise = TRUE）を持つ必要がある

```sql
-- 監督者割当作成時のトリガー
DELIMITER //
CREATE TRIGGER validate_supervisor_qualification BEFORE INSERT ON supervisor_assignments
FOR EACH ROW
BEGIN
    DECLARE has_qualification BOOLEAN;
    
    SELECT can_supervise INTO has_qualification
    FROM members WHERE member_id = NEW.supervisor_id;
    
    IF has_qualification = FALSE THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Assigned member must have supervisor qualification';
    END IF;
END //
DELIMITER ;
```

2. **パート所属の制約**
   - パート練習に参加するメンバーは、そのパートに所属している必要がある
   - 関連テーブル（MemberPart）で検証

3. **欠席申請との整合性**
   - 欠席申請が承認されたメンバーはセッションに割り当てられない
   - アプリケーションロジックで検証

#### 5.1.3 会場とセッションの整合性

1. **会場容量の制約**
   - セッションに割り当てられるパート数と各パートの最小必要人数の合計は会場の収容人数を超えてはならない
   - アプリケーションレベルで検証

2. **会場予約の排他制約**
   - 同一会場の同一時間帯に複数のセッションを予約できない
   - データベース制約で実装

```sql
-- ユニーク制約
ALTER TABLE practice_sessions
ADD CONSTRAINT unique_venue_time
UNIQUE (venue_id, date, start_time, end_time);
```

#### 5.3.2 権限によるデータアクセス制約

1. **ロールベースアクセス制御**

```sql
-- ロールごとにアクセス可能なビューの例
CREATE VIEW supervisor_schedules AS
SELECT s.* 
FROM schedules s
INNER JOIN supervisor_assignments sa ON s.schedule_id IN (
    SELECT DISTINCT ps.schedule_id 
    FROM practice_sessions ps
    INNER JOIN supervisor_assignments sa2 ON ps.session_id = sa2.session_id
    WHERE sa2.supervisor_id = CURRENT_USER_ID()
);
```

### 8.3 データアクセストランザクション

#### 8.3.1 トランザクション境界

アプリケーションのトランザクション境界を定義します。

```typescript
// トランザクション管理の例
interface TransactionManager {
  runInTransaction<T>(callback: (em: EntityManager) => Promise<T>): Promise<T>;
}

// サービスでの使用例
class ScheduleService {
  constructor(
    private scheduleRepo: ScheduleRepository,
    private sessionRepo: PracticeSessionRepository,
    private txManager: TransactionManager
  ) {}

  async createScheduleWithSessions(
    scheduleData: ScheduleCreateDTO, 
    sessionsData: SessionCreateDTO[]
  ): Promise<Schedule> {
    return this.txManager.runInTransaction(async (em) => {
      // トランザクション内で実行される操作
      const schedule = await this.scheduleRepo.save(scheduleData);
      
      for (const sessionData of sessionsData) {
        sessionData.scheduleId = schedule.id;
        await this.sessionRepo.save(sessionData);
      }
      
      return schedule;
    });
  }
}
```
