# 設計モデル詳細

## 1. 概要

本ドキュメントでは、練習表自動生成システムの設計において使用する各種設計モデルとその適用方法について詳細に説明します。本システムの設計・開発においては、適切な抽象化レベルでの設計モデルを用いることで、ステークホルダー間の共通理解を促進し、品質の高いシステム構築を目指します。

## 2. UMLモデル

### 2.1 クラス図

クラス図は本システムの静的構造を表現する主要なモデルです。特にドメインモデルの視覚化において重要な役割を果たします。

#### 2.1.1 概念レベルのクラス図

ドメインエキスパートとの対話を通じて得られた知識を整理し、ユビキタス言語を可視化するために使用します。システムのコアとなる概念とその関係性を日本語で表現し、属性やメソッドは主要なもののみを記載します。

**例: コアドメインモデルの概念図**

```
+------------------------+       +----------------------+
|        練習メニュー       |<>---->|         選手          |
+------------------------+       +----------------------+
| - メニューID             |       | - 選手ID             |
| - 名称                  |       | - 氏名               |
| - 所要時間               |       | - ポジション          |
| - 難易度                 |       | - 技術レベル          |
+------------------------+       +----------------------+
           ^                               ^
           |                               |
           |                               |
+------------------------+       +----------------------+
|      練習カテゴリ        |       |       チーム         |
+------------------------+       +----------------------+
| - カテゴリID            |       | - チームID           |
| - カテゴリ名             |       | - チーム名            |
| - 説明                  |       | - 監督                |
+------------------------+       +----------------------+
```

#### 2.1.2 詳細設計レベルのクラス図

実装に近いレベルで、システムの内部構造を表現します。クラス名、属性、メソッドを明確に定義し、アクセス修飾子や型情報も含めて記述します。

**例: 練習メニュー管理のクラス図**

```
+-------------------+       +-------------------+       +-------------------+
|   MenuRepository  |------>|      Menu         |<----->|  MenuCategory     |
+-------------------+       +-------------------+       +-------------------+
| + findById()      |       | - id: UUID        |       | - id: UUID        |
| + findAll()       |       | - name: String    |       | - name: String    |
| + save()          |       | - duration: int   |       | - description: String|
| + delete()        |       | - difficulty: int |       +-------------------+
+-------------------+       | + createMenu()    |
                           | + updateDuration() |

                                    |
                           +-------------------+
                           | MenuSpecification  |
                           +-------------------+
                           | - criteria: Map    |
                           | + isSatisfiedBy() |
                           +-------------------+
```

## 3. ER図

データベース設計において使用し、エンティティ間の関係を明確に表現します。

### 3.1 概念ER図

ドメインモデルに近い抽象度で、ビジネス要件を反映したデータ構造を表現します。エンティティ名やリレーションシップは日本語で記述し、ビジネス上の意味合いを明確にします。

**例: 練習管理の概念ER図**

```
+------------+       +------------+       +------------+
|    チーム   |-------|   練習表   |-------|  練習メニュー |
+------------+       +------------+       +------------+
       |                   |                    |
       |                   |                    |

+------------+       +------------+       +------------+
|    選手    |-------|  練習参加   |-------|  カテゴリ   |
+------------+       +------------+       +------------+
```

### 3.2 論理ER図

**例: 練習管理の論理ER図**

|     チーム      |        |     練習表       |        |   練習メニュー   |

| 創設日          |        | 作成者           |        | 難易度          |
| 活動場所        |        | ステータス        |        | FK カテゴリID   |
+----------------+        +------------------+        +----------------+
        |                        |                           |
        |                        |                           |
        ↓                        ↓                           ↓
+----------------+        +------------------+        +----------------+
|     選手       |        |  練習表明細       |        |   カテゴリ     |
+----------------+        +------------------+        +----------------+
| PK 選手ID      |        | PK 明細ID         |        | PK カテゴリID  |

## 6. 実装指針

各設計モデルの適用において、以下の点に留意します：

1. **適切な抽象化レベルの選択**：各モデルの目的と対象読者に合わせて、適切な抽象化レベルを選択します。

2. **一貫性の確保**：異なるモデル間で用語や概念の一貫性を保ち、ユビキタス言語に基づいた表現を心がけます。

3. **トレーサビリティの維持**：要件から設計、実装までのトレーサビリティを確保し、変更の影響範囲を把握しやすくします。

4. **段階的な詳細化**：概念レベルから物理レベルへと段階的に詳細化していくアプローチを採用し、利害関係者間のコミュニケーションを促進します。

5. **ツールと標準の活用**：UML標準に準拠したツールやノーテーションを活用し、設計の品質と一貫性を確保します。

## 7. 設計モデルの管理と更新

設計モデルは以下のルールに従って管理・更新します：

1. すべての設計モデルはバージョン管理システムで管理し、変更履歴を追跡します。
2. 重要な設計決定や変更は、設計レビューを経て承認されます。
3. 設計モデルの更新は、要件変更や実装フィードバックに基づいて計画的に行います。
4. 設計モデル間の整合性は定期的に確認し、不一致がある場合は速やかに修正します。
5. 設計モデルの標準化と再利用を促進し、設計の効率性と品質向上を図ります。
