# 実装指針：バックエンド（Python + Supabase）

## 1. 概要

本ドキュメントでは、練習表自動生成システムのバックエンド実装に関する指針について説明します。PythonとSupabaseを組み合わせたアーキテクチャにより、安定性、保守性、スケーラビリティを確保することを目的としています。

## 2. 技術スタック

### 2.1 コア技術

- **プログラミング言語**: Python
- **バックエンドプラットフォーム**: Supabase
- **データベース**: PostgreSQL（Supabase提供）
- **認証基盤**: Supabase Auth（JWT）
- **ストレージ**: Supabase Storage
- **WebフレームワークとAPI**: FastAPI
- **サーバーレス関数**: AWS Lambda / Vercel Functions
- **リアルタイム機能**: Supabase Realtime
- **データベースアクセス**: supabase-py + SQLAlchemy

### 2.2 開発ツール

- **開発環境**: Python 3.10+, Poetry
- **マイグレーション**: Alembic + SQL
- **テスト**: pytest + pytest-cov
- **型チェック**: mypy, pydantic
- **コード品質**: black, isort, flake8
- **API文書生成**: FastAPI自動ドキュメント生成（Swagger/OpenAPI）

### 3.2 テーブル設計の概要

練習表テーブル（schedules）は以下の要素で構成されます：

- プライマリキー（UUID）による一意識別
- チームへの参照（外部キー制約による整合性確保）
- 練習日時、場所などの基本情報
- ステータス管理（下書き、公開、アーカイブ）
- バージョン管理と監査情報（作成者、作成日時、更新日時）
- CHECK制約によるデータ整合性の確保

Row Level Security（RLS）ポリシーにより、権限に基づいたアクセス制御を実現します：
- チームメンバーのみが閲覧可能
- 管理者と編集者のみが作成・編集可能

自動更新日時トリガーにより、レコード更新時に更新日時フィールドが自動的に現在時刻に設定されます。これにより、データの監査履歴を正確に保持できます。

## 4. 認証と認可

### 4.1 認証フロー

Supabase Authを利用した認証フローを実装します：

- **ユーザー登録**: メールアドレス＋パスワード
- **ログイン**: JWTトークン発行
- **セッション管理**: クライアント側でのトークン保存・更新
- **パスワードリセット**: メール送信によるリセット

### 4.2 ロールと権限

Row Level Security（RLS）を使用して、以下のロールごとのアクセス制御を実装します：

| ロール | 権限 |
|-------|------|
| Admin | 全機能へのアクセス、ユーザー管理、設定変更 |
| Editor | 練習表の作成・編集、欠席管理 |
| Member | 練習表の閲覧、自身の欠席申請 |

チームメンバーテーブルでは、ユーザーとチームの多対多関係を管理し、各メンバーのロールを定義します。PostgreSQLのENUM型を使用してロールを厳密に管理し、不正な値が設定されることを防ぎます。メンバーシップ情報には加入日時も記録し、監査や分析に活用できます。

## 5. API設計

### 5.1 FastAPIを使用したREST API

Pythonでは、FastAPIを使用してREST APIを構築します。FastAPIは高速で、型ヒントを活用した自動ドキュメント生成機能を持つWebフレームワークです。

主な特徴：
- Pydanticによる強力なデータバリデーション
- OpenAPI準拠の自動ドキュメント生成（Swagger UI）
- 非同期処理のサポート
- 依存性注入システム
- セキュリティとOAuth2組み込み

Supabaseとの連携は、公式Pythonクライアント `supabase-py` を使用します：

```python
from supabase import create_client, Client
from fastapi import Depends, FastAPI, HTTPException

app = FastAPI()

# Supabaseクライアント初期化
supabase: Client = create_client(
    supabase_url=os.environ.get("SUPABASE_URL"),
    supabase_key=os.environ.get("SUPABASE_KEY")
)

# 依存性関数でSupabaseクライアントを提供
def get_supabase():
    return supabase

@app.get("/teams/{team_id}/schedules")
async def get_team_schedules(team_id: str, supabase: Client = Depends(get_supabase)):
    response = supabase.table("schedules").select("*").eq("team_id", team_id).execute()
    
    if response.error:
        raise HTTPException(status_code=400, detail=response.error.message)
        
    return response.data
```

FastAPIルーターを使用して、関連するエンドポイントをグループ化し、コードの整理と責任の分離を行います。

### 5.2 Lambda/サーバーレス関数

複雑なビジネスロジックや計算集約型の処理は、AWS LambdaやVercel Functionsなどのサーバーレス環境にPythonコードとしてデプロイします。

練習表生成機能のLambda関数実装では、以下の要素が含まれます：

1. **認証と認可**：
   - APIゲートウェイからのリクエストヘッダー処理
   - JWTの検証とユーザー情報の抽出
   - 権限チェックのためのSupabaseクエリ

2. **入力バリデーション**：
   - Pydanticモデルを使用した厳格な入力検証
   - カスタムバリデーター関数による複雑な制約条件の検証

3. **スケジュール生成アルゴリズム**：
   - NumPy、SciPyなどの科学計算ライブラリを活用した最適化
   - OR-Toolsなどの最適化ライブラリの使用
   - 並列処理による計算速度の向上

4. **データベース操作**：
   - Supabaseクライアントまたは直接的なPostgreSQLアクセス
   - SQLAlchemyを使用したトランザクション処理

5. **エラーハンドリング**：
   - 例外階層の定義と適切な例外処理
   - ステータスコードとエラーメッセージの標準化

Lambda関数は、serverless.ymlやAWS SAMなどのフレームワークを使用して管理・デプロイすることで、インフラストラクチャをコードとして扱うことができます。

## 6. データベーストリガーと関数

### 6.1 PostgreSQL関数の概要

スケジュール最適化や監督者ローテーション計算などの複雑なロジックは、PostgreSQL関数として実装します。

監督者ローテーション最適化関数の主な機能：

- チーム内の監督資格を持つメンバーを特定
- 練習セッションごとに最適な監督者を割り当て
- 公平な負荷分散のためのローテーションロジック
- カーソルを使用した効率的なデータ処理

関数はテーブル返却型を使用し、セッションIDと割り当てられた監督者IDのペアを返します。これにより、一度の呼び出しで複数のセッションに対する割り当てを効率的に行うことができます。

実装には宣言的なカーソル処理、条件分岐、ループ構造などのPL/pgSQLの機能を活用し、複雑なビジネスロジックをデータベース内で効率的に実行します。

### 6.2 データベーストリガーの概要

データの一貫性を保つためのトリガーを実装します。

欠席申請時のスケジュール再計算トリガーの主な機能：

- 欠席登録時に自動的に起動
- 影響を受けるスケジュールを特定（同じ日付、同じチーム）
- 再計算キューにタスクを挿入（優先度付き）
- 背後で実行される再計算処理のトリガー

このトリガーにより、メンバーが欠席を登録した際に、関連するスケジュールが自動的に再最適化されます。これにより、常に最新の出席情報に基づいた最適なスケジュールが維持されます。

トリガーの実装にはNEWレコード参照、サブクエリ、INSERT操作などの機能を活用し、データ変更時の自動アクションを実現します。

## 7. バッチ処理とスケジューリング

### 7.1 定期実行タスク

Supabaseではcronジョブを直接設定できないため、以下の方法で定期実行タスクを実装します：

1. **Supabase Functionsの定期実行**:
   - GitHub Actionsなど外部のスケジューラからSupabase Edge Functionsを定期的に呼び出す
   
2. **pgジョブ拡張機能**:
   - PostgreSQLのpg_cronなどの拡張機能を使用（Supabaseのプランによっては利用制限あり）

GitHub Actionsを使用した定期実行の設定では、cronシンタックスで実行スケジュールを定義し、APIエンドポイントを呼び出します。秘密情報（URLやトークン）はGitHub Secretsで安全に管理し、環境変数として提供します。

日次処理や週次処理など、複数の定期タスクは個別のワークフローとして定義し、それぞれに適切な実行頻度を設定します。

### 7.2 スケジュール生成バックグラウンドタスク

スケジュール生成などの重い処理は、Edge Functionsの処理時間制限を考慮して設計します：

1. **タスクキュー方式**:
   - 処理要求をデータベースのキューテーブルに格納
   - Edge Functionがポーリングして処理を実行
   - 処理状態を更新

タスクキューテーブルには以下の情報が格納されます：
- タスクの種類と詳細なパラメータ（JSONBフォーマット）
- 実行状態（保留中、処理中、完了、失敗）
- タイムスタンプ（作成日時、開始日時、完了日時）
- エラー情報と処理結果
- 処理優先度

タスク処理機能は「FOR UPDATE SKIP LOCKED」パターンを使用して、複数のワーカーが同時に異なるタスクを処理できるように設計されています。これにより、競合状態を避けつつ、並列処理による効率化を実現します。

優先度に基づいてタスクが処理されるため、緊急性の高いタスクを先に実行することができます。

## 8. エラー処理と例外管理

### 8.1 クライアントエラーハンドリングの概要

クライアント側でのエラーハンドリングは、以下の原則に基づいて設計されています：

- Supabaseクライアントから返されるエラーオブジェクトの詳細な解析
- エラーコードに基づいた適切なユーザーフレンドリーなメッセージへの変換
- エラーのログ記録と通知メカニズム
- 適切な例外スローによる上位レイヤーへのエラー伝播

主なエラーパターンとその処理：
- データ未検出（404）：該当リソースが見つからないケース
- 認証エラー（401）：認証情報の不足や無効化
- 権限エラー（403）：認証されたが権限不足
- バリデーションエラー：データ形式や制約違反
- ネットワークエラー：接続問題

実装には try-catch パターンを使用し、エラー発生時のグレースフルデグラデーション（機能の段階的な低下）を確保します。

### 8.2 FastAPIでのエラーハンドリング

FastAPIでは、Python標準の例外処理メカニズムとHTTPExceptionクラスを組み合わせて、堅牢なエラーハンドリングを実現します：

```python
from fastapi import FastAPI, HTTPException
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from starlette.exceptions import HTTPException as StarletteHTTPException
from pydantic import ValidationError

app = FastAPI()

# カスタム例外クラス
class DomainException(Exception):
    def __init__(self, message: str, code: str):
        self.message = message
        self.code = code
        super().__init__(self.message)

# 例外ハンドラ
@app.exception_handler(DomainException)
async def domain_exception_handler(request, exc: DomainException):
    return JSONResponse(
        status_code=400,
        content={"message": exc.message, "code": exc.code},
    )

@app.exception_handler(RequestValidationError)
async def validation_exception_handler(request, exc: RequestValidationError):
    errors = exc.errors()
    error_messages = []
    for error in errors:
        error_messages.append({
            "field": error["loc"][-1] if len(error["loc"]) > 0 else "",
            "message": error["msg"],
            "type": error["type"]
        })
    
    return JSONResponse(
        status_code=422,
        content={"message": "入力データが無効です", "details": error_messages},
    )
```

主な特徴：
- 一貫した例外処理パターン
- APIレスポンスの標準化
- エラーのタイプ、場所、メッセージなどの詳細情報の提供
- 開発環境と本番環境での異なるエラー詳細レベル

## 9. データ移行とバージョニング

### 9.1 データベースマイグレーションの概要

データベースのスキーマ変更は、マイグレーションファイルとして管理されます。各マイグレーションファイルには以下の要素が含まれます：

- テーブルやカラムの追加・変更・削除
- 制約条件の設定や変更
- インデックスの作成や最適化
- 既存データの変換や更新
- トリガーや関数の定義

マイグレーションは累積的に適用され、データベースの状態を段階的に変更します。各マイグレーションには、問題が発生した場合に変更を元に戻すためのロールバックロジックも含まれることがあります。

具体的なスキーマ変更の例としては、新機能追加のためのカラム追加、検索パフォーマンス向上のためのインデックス作成、データ整合性向上のための制約追加などがあります。

### 9.2 マイグレーション管理の概要

Supabase CLI を使用してマイグレーションを管理します。主なコマンドとその用途：

- **migration new**：新しいマイグレーションファイルのテンプレート作成
- **db reset**：ローカル開発環境のデータベースをリセットし、すべてのマイグレーションを再適用
- **db push**：本番環境にマイグレーションを適用

マイグレーション管理のベストプラクティス：
- 各マイグレーションは１つの論理的な変更に限定する
- マイグレーションにはわかりやすい命名規則を適用する
- バージョン番号またはタイムスタンプによるファイル名の付与
- マイグレーション適用前のバックアップ実施
- 開発環境での十分なテスト後に本番適用

このアプローチにより、データベーススキーマの変更を安全に管理し、開発チーム間での協業を円滑にします。

## 10. パフォーマンス最適化

### 10.1 データベース最適化の概要

データベースパフォーマンスを最適化するため、以下の戦略を採用します：

**インデックス最適化**：
- 頻繁にフィルタリングされるカラムにインデックスを作成
- 複合インデックスを使用して複数条件での検索を最適化
- 特殊なデータ型（GINなど）を活用して配列や全文検索をサポート

**ビューの活用**：
- 複雑なクエリをビューとして定義し、再利用性を向上
- 結合やサブクエリを含む処理をデータベース側で最適化
- アプリケーションロジックの簡素化と一貫性確保

**クエリチューニング**：
- EXPLAIN ANALYZEを使用したクエリプラン分析
- N+1クエリ問題の回避（一度に必要なデータを取得）
- 適切なウィンドウ関数やCTEの活用

これらの最適化により、特に大量のスケジュールデータや多数のチームメンバーが存在する場合でも、高速なレスポンスタイムを維持します。

### 10.2 キャッシュ戦略の概要

Supabaseの自動API生成はPostgRESTを使用しているため、標準的なHTTPキャッシング技術を適用できます。

- **Cache-Control ヘッダー**: 静的なリソースへの設定
- **ETags**: リソースの変更検出
- **クライアントサイドキャッシング**: React Queryなどのライブラリでの利用

クライアント側でのキャッシュ戦略：
- 頻繁にアクセスされるが更新頻度の低いデータの一時保存
- staleTimeとcacheTimeの適切な設定によるリフレッシュ制御
- 楽観的更新による即時UIフィードバック
- バックグラウンドでの定期的なデータ再検証

サーバーサイドでのキャッシュ最適化：
- 複雑な集計クエリの結果をマテリアライズドビューとして保存
- 定期的な更新スケジュールの設定
- 部分的なキャッシュ無効化メカニズム

これらの戦略により、API呼び出しの回数を削減し、アプリケーションの応答性を向上させます。

## 11. セキュリティ対策

### 11.1 データベースセキュリティの概要

機密データの保護のため、以下のセキュリティ対策を実装します：

**データ暗号化**：
- pgcrypto拡張を使用した特定カラムの暗号化
- 電話番号、緊急連絡先、医療情報などの機密情報の保護
- 暗号化キーの安全な管理

**Row Level Security（RLS）の詳細設計**：
- ユーザー自身のデータにのみアクセス可能なポリシー
- 管理者向けの特別なアクセス権限ポリシー
- 複雑な条件式を使用したきめ細かなアクセス制御

**監査とログ記録**：
- 重要な操作の監査ログテーブル
- 変更履歴の自動記録
- アクセスパターンのモニタリング

これらの対策により、個人情報や機密データが適切に保護され、必要な権限を持つユーザーのみがアクセスできる環境を確保します。

### 11.2 APIセキュリティの概要

API層でのセキュリティを強化するため、以下の対策を実装します：

**レート制限**：
- ユーザーIDまたはIPアドレスごとのリクエスト制限
- 時間ウィンドウベースの制限（例：1分間に60リクエストまで）
- 異常なアクセスパターンの検出と遮断

**入力検証**：
- zod/yupなどのライブラリを使用した厳格なスキーマ検証
- すべてのユーザー入力の検証
- SQLインジェクションやXSS対策のためのエスケープ処理

**CSRF対策**：
- トークンベースの検証
- Origin/Refererヘッダーの確認
- Same-Site Cookie設定

**JWTセキュリティ**：
- 適切な有効期限設定
- セキュアな署名アルゴリズム（RS256など）
- トークンローテーションとリフレッシュメカニズム

これらの対策を組み合わせることで、APIエンドポイントへの不正アクセスやデータ漏洩のリスクを最小化します。

## 12. テスト戦略

### 12.1 単体テストの概要

Pythonバックエンドの単体テストでは、pytestフレームワークを使用し、以下のアプローチを採用します：

**テストセットアップ**:
- fixtureによるテスト環境の準備
- モックオブジェクトによる外部依存の代替
- ファクトリーパターンによるテストデータ生成

```python
import pytest
from unittest.mock import Mock, patch
from app.services.schedule_generator import ScheduleGenerator

@pytest.fixture
def mock_supabase():
    """Supabaseクライアントのモック"""
    mock = Mock()
    mock.table.return_value.select.return_value.execute.return_value.data = [
        {"id": 1, "name": "テストチーム"}
    ]
    return mock

def test_generate_schedule(mock_supabase):
    """スケジュール生成機能のテスト"""
    generator = ScheduleGenerator(supabase_client=mock_supabase)
    result = generator.generate(team_id=1, start_date="2023-01-01", end_date="2023-01-31")
    
    # 結果の検証
    assert len(result) > 0
    assert all("date" in session for session in result)
    
    # Supabaseクライアントの呼び出し検証
    mock_supabase.table.assert_called_with("teams")
```

**パラメータ化テスト**:
- 様々な入力パターンの効率的なテスト
- 境界値と異常値のケース網羅

### 12.2 統合テストの概要

**FastAPI TestClient**:

- リクエスト/レスポンスサイクルの完全テスト
- 認証フローの検証

from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

def test_create_schedule_api():
    """スケジュール作成APIのテスト"""
    # 認証（テスト用トークンの取得）
    auth_response = client.post(
        "/auth/token",
        data={"username": "test@example.com", "password": "testPassword"}
    )
    token = auth_response.json()["access_token"]
    
    # スケジュール作成リクエスト
    response = client.post(
        "/schedules/",
        headers={"Authorization": f"Bearer {token}"},
        json={
            "team_id": 1,
            "date": "2023-05-01",
            "location": "テスト会場",
            "start_time": "13:00",
            "end_time": "15:00"
        }
    )
    
    # レスポンスの検証
    assert response.status_code == 201
    data = response.json()
    assert "id" in data
    assert data["team_id"] == 1
